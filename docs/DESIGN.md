# 솔버 엔진 설계

작성 2026-11-24 · 상태: 초안 (검토 후 확정)

## 1. 목표와 범위

**목표:** 내 PC에서 헤즈업 포스트플랍 스팟을 수 분 안에 풀어주는 개인용 솔버.

| 포함 | 제외 (나중에) |
|---|---|
| NLHE 헤즈업 포스트플랍 | 프리플랍 계산 (레인지는 입력으로 받음) |
| 리버 → 턴 → 플랍 순서로 확장 | 3인 이상 멀티웨이 |
| 사용자 지정 벳/레이즈 사이즈 | ICM, 레이크 (구조만 열어둠) |
| 익스플로이터빌리티 측정 | 노드 락 (2차 목표) |

## 2. 전체 구조

```
solver/
├─ engine/        Rust 라이브러리. 솔버 엔진 전부 (UI 의존성 0)
├─ cli/           Rust 실행파일. 엔진을 터미널에서 돌려보는 테스트용
├─ app/           Tauri + TypeScript. 마지막 단계에 추가
├─ learning/      학습용 코드 (Kuhn 등)
└─ docs/
```

- 엔진은 **UI를 모르는 순수 라이브러리**로 만든다. CLI와 Tauri 앱이 같은 엔진을 가져다 쓴다.
- 엔진이 완성되기 전까지는 CLI로만 확인한다.

## 3. 엔진 API (UI와의 약속)

이 인터페이스는 엔진 내부가 바뀌어도 유지한다.

```rust
// 설정
struct SolveConfig {
    board: Vec<Card>,              // 3~5장
    oop_range: Range,              // 아웃오브포지션 레인지 (1326 콤보 가중치)
    ip_range: Range,               // 인포지션 레인지
    pot: f32,
    effective_stack: f32,
    bet_sizes: BetSizeConfig,      // 스트리트·포지션별 벳/레이즈 % 목록
    target_exploitability: f32,    // 팟 대비 % (예: 0.5)
    max_iterations: u32,
}

fn solve(config, on_progress: impl Fn(Progress), cancel: &AtomicBool) -> Solution;

impl Solution {
    fn root() -> NodeId;
    fn children(node) -> Vec<(Action, NodeId)>;
    fn strategy(node) -> Strategy;   // 콤보별 액션 확률
    fn ev(node, player) -> Vec<f32>; // 콤보별 EV
    fn equity(node, player) -> Vec<f32>;
}
```

- `Progress` = { 반복 횟수, 현재 익스플로이터빌리티 }
- 취소는 공유 플래그(`AtomicBool`)를 반복마다 확인하는 방식
- Tauri에서는 `solve`를 워커 스레드에서 돌리고 `on_progress`에서 `emit`

## 4. 핵심 데이터 구조

### 카드와 콤보
- `Card` = `u8` (0~51). `rank = c / 4`, `suit = c % 4`
- 콤보(핸드 2장) = 0~1325 인덱스. 1326개 고정 테이블
- `Range` = `[f32; 1326]` (콤보별 가중치 0~1)
- 보드와 겹치는 콤보는 시작할 때 제외하고, 남은 콤보만 압축된 인덱스로 다룬다

### 핸드 평가기
- 7장(보드 5 + 핸드 2) → 강도 값(`u16`, 클수록 강함)
- 처음엔 단순하고 맞는 구현, 나중에 룩업 테이블로 최적화
- 검증: 7장 조합 1억 3천만 개 전수 돌려 족보별 개수가 알려진 값과 일치하는지

### 게임 트리
- **Arena 방식**: 모든 노드를 `Vec<Node>` 하나에 넣고 인덱스로 연결 (포인터/Box 트리 X)
- 노드 종류: `Action`(플레이어 결정), `Chance`(턴·리버 딜), `Terminal`(폴드/쇼다운)
- 액션 노드의 숫자 데이터는 노드 안에 두지 않고 **큰 연속 배열 하나에 오프셋으로** 둔다

```
Node { kind, player, children: Range<u32>, data_offset: u32, ... }

regrets:   Vec<f32>   // [노드A 콤보0 액션0, 콤보0 액션1, ..., 노드B ...]
strat_sum: Vec<f32>   // 같은 배치
```

이게 "데이터 지향" 설계의 핵심. CPU 캐시와 SIMD에 유리하고 메모리 계산이 쉽다.

## 5. 알고리즘

### Kuhn 코드와의 차이: 벡터 방식
- Kuhn 코드는 카드를 **무작위로 한 번 딜**하고 그 경우만 계산했다 (샘플링).
- 실제 엔진은 트리를 한 번 내려갈 때 **양쪽 레인지 전체(콤보 벡터)를 한꺼번에** 들고 간다.
  - 내려갈 때: 콤보별 도달 확률 벡터
  - 올라올 때: 콤보별 EV 벡터
- 찬스 노드(턴·리버)는 샘플링하지 않고 모든 카드를 순회한다.

### CFR 변형: DCFR (Discounted CFR)
- 기본 CFR에 "오래된 regret은 할인"을 추가한 것. 수렴이 훨씬 빠르다.
- 파라미터: α=1.5, β=0, γ=2 (논문 권장값)
- 양 플레이어를 번갈아 업데이트 (alternating updates)

### 쇼다운 계산 최적화
- 단순 계산: 내 콤보 × 상대 콤보 = O(n²)
- 콤보를 핸드 강도순으로 정렬하고 누적합으로 처리 → **O(n)**
- 카드가 겹치는 콤보(블로커)는 카드별 누적값을 빼서 보정
- 리버 보드마다 (강도, 콤보 번호, 카드 2장)을 강도순 연속 배열로 저장 → 간접 참조 없이 훑음
- 가치 = 무승부 지급 × 겹치지 않는 상대 + (이김 − 무승부) × 약한 상대 + (짐 − 무승부) × 강한 상대 (f64 누적)
- 테스트: 모든 콤보 쌍을 직접 비교한 결과와 일치 (`showdown_matches_brute_force`)

### 수트 동형성 (0.2.0)
- 찬스 노드에서 두 수트가 **보드에서 랭크 구성이 같고**(예: 둘 다 보드에 없음) **양쪽 레인지가 두 수트를 바꿔도 같으면**, 그 수트의 카드는 낮은 수트 카드(대표)와 같은 상황
- 대표 카드만 하위 트리를 만들고, 동형 카드의 가치 = 대표 카드 결과에서 콤보의 수트를 바꾼 값 (`swap_map`)
- 효과: 투톤 플랍(남는 수트 2개) 턴 49장 → 36장, 모노톤 49 → 23장, 페어 보드도 일부. 레인보우는 플랍 단계에선 효과 없음
- 트리 탐색(`walk_full`)은 실제 고른 카드 ↔ 트리 카드의 수트 치환을 들고 다녀서, 화면에는 실제 카드와 보드가 보임
- 테스트: 균등 전략에서 전부 펼친 트리와 콤보별 EV·익스플로이터빌리티 일치, 동형 카드 경로 = 대표 카드 경로

### 병렬화·메모리 접근
- 찬스 노드 자식 + **하위 트리가 400노드 넘는 액션 노드의 자식**을 rayon으로 병렬 (턴·리버 트리도 코어를 다 씀)
- f32 저장소는 regret·누적 전략을 복사 없이 제자리에서 갱신. 16비트 압축은 풀고 → 갱신 → 다시 압축
- 액션 행 단위 연속 루프 (SIMD), x86-64-v2 빌드 (`.cargo/config.toml`)

### 익스플로이터빌리티
- 현재 평균 전략에 대해 각 플레이어의 **최적 대응(best response)** EV를 계산
- `(BR_oop + BR_ip − 팟) / 2 / 팟 × 100` = 팟 대비 %
- 목표값 이하가 되면 종료

설계 문서와 달라진/구체화된 점
- **손익 기준**: 폴드 시 이긴 쪽 = 시작팟 + 진 쪽이 넣은 칩, 진 쪽 = −자기가 넣은 칩. 쇼다운 무승부 = 시작팟/2. 그래서 두 EV의 합 = 시작팟
- **찬스 확률**: 카드 한 장 확률 = 1 / (52 − 보드 장수 − 4). 양쪽 핸드 4장을 뺀 덱 기준. 내 핸드·상대 핸드와 겹치는 카드는 reach/결과를 0으로 처리
- **평균 전략 누적**: 상대 차례 노드를 지날 때 누적 (이때 들고 있는 reach가 그 노드 주인의 도달 확률이므로)
- **API**: `Game::new(&SolveConfig)` (수트 동형성 자동, 끄려면 `Game::with_isomorphism(cfg, false)`) → `Solver::new(game)` → `solver.run(max_iter, target%, check_every, &cancel, on_progress)`. 조회는 `strategy(node)`, `walk(path)`/`walk_full(path)`, `summarize(path)`, `expected_values()`, `node_hand_evs(node, p, opp_reach)`
- **노드 EV**: 모든 액션 노드에서 핸드별 EV = 지금 팟에서 앞으로 가져갈 기대 칩 − 앞으로 더 넣을 칩
- **병렬화**: 찬스 노드 자식(카드별 하위 트리)을 rayon으로 병렬 처리. 노드마다 저장 구간이 겹치지 않아서 안전 (`solver.rs`의 `Ptr` 주석 참고)

### 외부 솔버 비교 (미완료)
- 계획: postflop-solver(AGPL)를 **저장소 밖**에서 빌드해 같은 스팟을 풀고 루트 전략·EV 비교. 코드는 가져오지 않음
- 2026-11-25: 비교용 하니스는 빌드됐지만, 내려받은 외부 코드 실행이 자동 승인 정책에 막혀 실행 못 함 → 사용자가 직접 실행하거나 허용 필요
- 그 전까지의 검증: 이론 토이 게임 일치, 턴=리버 평균 일치, 익스플로이터빌리티 단조 감소 (익스플로이터빌리티는 그 자체로 "얼마나 정답에서 먼지"의 엄밀한 척도)
